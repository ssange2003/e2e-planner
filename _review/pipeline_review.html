01

결론 먼저

모듈 구조(DatasetLoader → SensorEvidence → ScenarioClassifier → LabelProcessor → Augmentor)는 요구사항과 이미 정확히 일치한다. 구조를 다시 쓸 필요는 없다. 문제는 전부 그 안에 채워진 값과 판정식에 있고, 대부분 한 줄에서 몇 줄 수준의 수정으로 고쳐진다.

다만 그중 셋은 "튜닝"이 아니라 기능이 죽어 있는 상태다. 지금 파이프라인이 그럴듯한 결과를 내는 이유는 파일명 prior가 죽은 센서 로직을 대신 떠받치고 있기 때문이다. 파일명을 떼면 S구간 검출은 0%다.

02

가장 중요한 발견: 섹터를 잘못 골랐다

config.py는 측면 라이다를 이렇게 정의한다. 

FRONT_LIDAR_COL = "lidar_s2"
SIDE_LIDAR_COLS = ["lidar_s1", "lidar_s3"]   ← 이게 측면이 아니다

부가 소득

실측값을 역산하면 유효 측방 여유는 0.2m가 아니라 약 0.32m다 (s0: 0.382 = 0.32/sin 59.8°, s1: 0.636 ≈ 0.32/sin 29.9° — 두 섹터가 같은 값으로 수렴). 차선폭 40cm 가정보다 차량이 여유 있게 지나가고 있다는 뜻이므로, 임계값을 0.45m로 두면 s0/s4 기준에서 적절한 마진이 된다.

YOLO는 종이컵을 볼 수 없다 — 클래스에 존재하지 않는다

yolo_config.py의 13개 클래스는 BFMC 대회용 표지판·차량·보행자다. one_way_road_sign, stop_sign, pedestrian, car … 종이컵은 어느 클래스에도 해당하지 않는다. 기존 코드 주석은 이를 "카메라 파이프라인이 개선되면 자동으로 다시 유효해진다"고 적어두었지만, 실제로는 모델을 다시 학습시키기 전까지 영원히 False다. 현재 이 코스에서 cam_threat, CAMERA_OBJ_DANGER_NORM, 그리고 그에 딸린 모든 판정 분기는 실행되지 않는 죽은 코드다.

F‑06치명코드 확인

depth 구멍이 "가장 먼 거리"로 기록된다 — 부호가 뒤집혀 있다

# collect_data_planner.py : _yolo_worker
raw  = int(depth_array[cy, cx])
dist = raw * depth_scale if raw > 0 else -1.0

# planner_model.py : build_object_features
dist_norm = min(max(dist,0), MAX_DIST_M)/MAX_DIST_M if dist > 0 else 1.0
#                                                                    ↑ 1.0 = 5m = 가장 멂

D435가 depth를 못 읽으면(무텍스처·최소거리 미만·과노출) raw = 0이 되고, 이 값은 -1을 거쳐 dist_norm = 1.0, 즉 "5m 밖"으로 기록된다. 가장 가까워서 못 읽은 물체가 가장 먼 물체로 학습되는 구조다. Behavior Cloning 관점에서 이보다 나쁜 라벨 오염은 드물다. valid=0으로 빼거나 별도 dist_unknown 플래그를 두어야 한다.

특히 MIN_STOP_FRAMES가 요구사항 §6을 직접 훼손한다

0.5초 미만의 짧은 정지는 is_stop = False가 되고, stop_state에 들어가지 못해 재출발 상태머신이 아예 열리지 않는다. "STOP → RECOVERY가 매우 중요"하다면 이 값은 10fps 기준 2(0.2초)로 낮추고, 대신 증거 강도로 걸러야 한다.

05

RECOVERY가 1프레임만 라벨된다

요구사항 §6은 0 → 0.4 → 0.7 → 0.85 → 0.95 전체 transition이 재출발 행동이라고 명시한다. 현재 구현은 그렇지 않다. 

# scenario.py — 현재
if awaiting and thr[i] > MOTOR_DEAD_ZONE_MAX and (clr[i] or relax_clear):
    is_recovery.loc[idx[i]] = True   ← breakaway를 넘은 그 한 프레임만
    awaiting = False

실측에서 4개 파일 전체 recovery 프레임이 10개에 불과한 것이 그 증거다 (파일당 2~4개 = 이벤트당 1프레임). 0.4와 0.7 프레임은 RECOVERY 라벨을 받지 못하며, is_protected의 ±2 dilation에 우연히 걸려야만 스무딩을 면한다. 보호는 우연에 맡기고 라벨은 잃는 구조다.

고쳐야 할 방향

"정지 종료" 시점부터 "breakaway 최초 초과" 시점까지 구간 전체를 RECOVERY로 칠해야 한다. 아래 §7에 교체 코드를 실었다.

APPROACHING과 CLEARED는 요구사항대로 내부 상태로만 두고 최종 라벨로 저장하지 않아도 된다. 다만 파생 피처로는 반드시 내보내야 한다 — 이유는 다음 절에.

S구간이 이 전이도에 들어가면 안 되는 이유

S구간은 상태가 아니라 맥락이다. 좌우가 좁은 채로 NORMAL·AVOIDANCE·STOP이 전부 일어날 수 있다. 현재 코드가 is_s_curve를 우선순위 표에서 AVOIDANCE보다 낮게 둔 것은 옳은 선택이다. 다만 라벨이 아니라 불리언 맥락 플래그로 분리하고, STOP 증거 판정에서 "정면 위협을 STOP으로 승격하지 않는" 게이트로만 쓰는 편이 명확하다.

STOP과 RECOVERY는 모델 입력상 구분이 불가능하다

"정지 3초째"와 "정지 0.1초째"는 센서 관측이 동일하다. 정면도 똑같이 막혀 있고, lane도 같고, prev_throttle도 둘 다 0이다. 모델이 언제 재출발해야 하는지 알 수 있는 정보가 입력에 존재하지 않는다. 전처리에서 RECOVERY 라벨을 아무리 정성껏 보존해도, 모델은 같은 입력에 서로 다른 출력이 달린 모순 샘플로 받아들이고 그 평균(≈ 어중간한 스로틀)을 학습한다.

scenario=STOP을 입력으로 주면 모델은 "STOP이면 throttle=0"이라는 자명한 규칙만 배운다. 그런데 추론 시점에는 STOP인지 모른다 — 그게 바로 예측해야 할 대상이다. 이건 causal confusion의 교과서적 사례다. scenario는 "차선주행 / 주차" 같은 임무 명령으로만 남기고, 상태는 위의 파생 피처로 넣어야 한다.

08

D435 / D435i를 제대로 쓰는 법

현재 camera.py는 depth 스트림을 켜고 정렬까지 해놓고, 그 결과를 YOLO 바운딩박스 중심 픽셀 1개로만 소비한 뒤 버린다. 848×480 = 40만 픽셀의 깊이 정보 중 실제로 쓰이는 건 프레임당 최대 5픽셀이다. 그리고 §03에서 봤듯 그 5픽셀조차 거의 항상 발생하지 않는다.

D‑01중대

측면 종이컵은 카메라로 볼 수 없다 — 역할 분담이 맞다

0.2m 옆의 컵이 depth FOV(±43.5°) 안에 들어오려면 종방향 거리가 0.21m 이내여야 하는데, 그건 이미 Min-Z 경계다. 측면은 라이다(s0/s4), 정면은 카메라라는 현재의 암묵적 분담은 물리적으로 옳다. 카메라로 S구간 폭을 재려는 시도는 하지 말 것.

D‑02치명

IR 프로젝터 설정이 없다 — 흰 종이컵은 무텍스처다

D435는 active IR stereo다. 흰 종이컵처럼 텍스처가 없는 표면은 IR 패턴 프로젝터 없이는 스테레오 매칭이 실패해 depth 구멍이 된다. 현재 camera.py에는 emitter 관련 코드가 전혀 없어 SDK 기본값에 의존하고 있다. 이것이 obj_dist가 신뢰할 수 없는 근본 원인 중 하나다. 

# camera.py __init__ 에 추가
depth_sensor.set_option(rs.option.emitter_enabled, 1)
depth_sensor.set_option(rs.option.laser_power, 240)   # 최대 360
depth_sensor.set_option(rs.option.visual_preset,
                        rs.rs400_visual_preset.high_density)

장애물 존재 여부가 중요하므로 high_accuracy(구멍 많음)보다 high_density가 맞다. 정밀 측距가 아니라 "막혔나?"를 묻는 작업이기 때문이다.

D‑03중대

후처리 필터가 하나도 적용되지 않았다

RealSense SDK가 제공하는 spatial / temporal / hole-filling 필터가 전혀 쓰이지 않은 채 단일 픽셀을 샘플링하고 있다. 이 조합은 최악이다 — 필터 없는 raw depth의 픽셀 단위 노이즈와 구멍을 그대로 맞는다. 최소한 bbox 내부 ROI의 유효값 중앙값으로 바꾸는 것만으로도 크게 개선된다. 

# _yolo_worker — 단일 픽셀 → ROI 중앙값
x1,y1,x2,y2 = [int(v) for v in box]
mx, my = int((x2-x1)*0.25), int((y2-y1)*0.25)   # 내부 50%만
roi = depth_array[y1+my:y2-my, x1+mx:x2-mx]
valid = roi[roi > 0]

D‑04중대 · 최대 기회

depth를 라이다처럼 섹터화하면 종이컵이 보인다

YOLO 클래스에 없는 물체를 감지하는 유일한 방법이다. depth 이미지 하단부를 세로 컬럼으로 나눠 각 컬럼의 유효 depth 하위 백분위수를 취하면, 클래스에 무관한 정면 자유공간 프로파일이 나온다. 

# 새 함수 — collect_data_planner.py
def depth_to_free_space(depth_m, n_cols=9, row_lo=0.45, row_hi=0.95):
    h, w = depth_m.shape
    band = depth_m[int(h*row_lo):int(h*row_hi), :]
    out = []
    for c in np.array_split(np.arange(w), n_cols):
        col = band[:, c[0]:c[-1]+1]
        v = col[(col > 0.15) & (col < 4.0)]
        out.append(float(np.percentile(v, 5)) if v.size >= 20 else 4.0)
    return out          # depth_c0 … depth_c8

라이다 대비 이점이 분명하다. 라이다는 단일 수평면만 스캔하므로 마운트 높이보다 낮거나 높은 장애물을 놓치지만, depth는 높이 방향 정보를 포함한다. 종이컵처럼 낮은 물체에 특히 유효하다.

D‑05D435i 한정

IMU가 있다면 "실제로 멈췄는가"를 알 수 있다

D435i에는 BMI055 IMU(accel 250Hz / gyro 200Hz)가 들어 있고, 현재 스트림을 켜지 않고 있다. 이게 해결해주는 문제가 큰데, 지금 파이프라인은 "명령 throttle이 0"인 것만 알 뿐 차량이 실제로 정지했는지 모른다.

  • STOP 증거가 명령값 추론에서 물리 측정으로 승격된다 — 지금까지 논의한 zero-event 판정 로직 상당 부분이 불필요해진다
  • MOTOR_DEAD_ZONE_MAX = 0.85를 추측이 아니라 실측 캘리브레이션으로 확정할 수 있다
  • 요레이트를 얻으면 조향 정규화값 ↔ 실제 조향각 관계가 확정된다 (현재 저장소 어디에도 축거·속도 캘리브레이션 값이 없다)
  • 노이즈 zero-event와 진짜 정지가 가속도계로 즉시 구분된다
cfg.enable_stream(rs.stream.accel, rs.format.motion_xyz32f, 250)
cfg.enable_stream(rs.stream.gyro,  rs.format.motion_xyz32f, 200)

먼저 rs-enumerate-devices로 D435인지 D435i인지 확인하는 것이 순서다.

D‑06보통

자동 노출이 차선 세그멘테이션을 흔들고 있을 가능성

s_curve 코스의 lane grid 합이 중앙값 0.04, 31%가 완전히 0이다(F‑07). BiSeNet이 이 구간에서 차선을 거의 못 잡는다는 뜻인데, 프레임마다 변하는 자동 노출이 원인의 일부일 수 있다. 노출을 고정하거나 ROI를 노면으로 한정해 재수집 시 비교해볼 값이 있다. 다만 컵 코스에 애초에 차선 도색이 없다면 이건 정상이며, 그 경우 lane 증거는 이 코스에서 사용을 포기하는 것이 맞다.
